FROM REPORT TO WORKING EXPERIENCE

An accessibility report doesn’t fix anything by itself.

An audit tells you where barriers exist. Remediation changes the website so those barriers are no longer present.

That can mean correcting HTML structure, rebuilding a custom component, changing CSS, improving keyboard interaction, fixing form relationships, or making content easier to understand.

EqualAccess. can take the findings beyond the spreadsheet and into the website.

Start with Accessibility Audits & Testing

ONE ILLUSTRATIVE MENU FINDING

  1. AUDIT

    “Keyboard user cannot open menu.”

    A finding identifies the barrier.

  2. TECHNICAL INVESTIGATION

    Find the cause.

    Inspect event handling, semantics, focus, and component state.

  3. REMEDIATION

    Correct the component.

    Change the underlying interaction, then test what changed.

  4. RETEST

    Repeat the affected journey.

    Use keyboard controls and relevant assistive technology.

  5. VERIFIED

    Confirm the tested outcome.

    The menu works as intended in the tested environment.

Finding barriers is step one. Removing them is the part your users actually experience.

REAL REMEDIATION

Accessibility should be built into the website.

We focus on the theme, templates, components, content, and interactions themselves. An accessibility widget or overlay is not a substitute for fixing inaccessible code.

Sometimes the right fix is a better HTML element. Sometimes it needs CSS, JavaScript, ARIA, content changes, or a combination of them.

THE TECHNICAL WORK

From basic HTML problems
to complex user interactions.

Accessibility barriers can exist throughout a website. The remediation scope depends on what testing finds and how the website is built.

01

Structure

<main> · <h1> · <table>

Semantic structure
Correct headings, landmarks, lists, tables, page structure, relationships, and missing or inappropriate HTML elements.
Images & icons
Improve meaningful text alternatives and ensure decorative graphics do not create unnecessary screen-reader noise.
02

Keyboard

Tab · Enter · Escape

Keyboard accessibility
Make navigation, filters, product options, forms, and dialogs reachable and operable without a mouse.
Focus management
Correct missing focus indicators, illogical movement, keyboard traps, focus loss, and focus handling when interfaces change.
03

Forms

Label · Instruction · Error

Forms & validation
Connect labels and instructions, communicate required fields, explain errors, and correct programmatic relationships.
Status & error messages
Make relevant errors, success states, loading messages, cart changes, and search results available to assistive technology.
04

Navigation

Name · State · Interaction

Navigation & menus
Improve submenu behavior, keyboard operation, current states, focus order, skip mechanisms, and mobile navigation.
Accessible names & controls
Correct missing, unclear, duplicated, or inappropriate names for buttons, links, fields, icons, and custom controls.
05

Components

Role · State · Focus

ARIA & dynamic interfaces
Correct roles, states, properties, live updates, expandable controls, and custom widgets where ARIA is appropriate.
Dialogs & modals
Correct naming, initial focus, keyboard access, focus containment, closing behavior, and focus return.
06

Visual presentation

Contrast · Reflow · Zoom

Contrast & visual states
Correct text and interface contrast, visible focus, selected states, and information conveyed only through color where editable.
Responsive & zoom behavior
Address content that disappears, overlaps, clips, or becomes unusable when enlarged or reflowed.

BEFORE → FIX → VERIFY

See the difference between
finding an issue and resolving it.

Choose an example, inspect the change, and try the corrected interaction. These are isolated demonstrations—not a live accessibility scan or proof that a whole website conforms.

Menu / illustrative example

A menu that works without a mouse.

BEFORE

The dropdown opens on hover, but keyboard users cannot reliably open its links.

User impact Important pages can become unreachable for someone navigating with a keyboard.

THE FIX

Use a native button, expose the expanded state, and support opening, navigating, and closing the disclosure.

Menu code example
<button aria-expanded="false"
  aria-controls="product-links">
  Products
</button>
<ul id="product-links" hidden>…</ul>

The button toggles the list and aria-expanded. Escape closes it and returns focus to the trigger; Tab follows the visible links.

AFTER TRY THE CORRECTED PATTERN

Try Tab, Enter, and Escape.

HOW WE VERIFY

Keyboard interaction and expanded state retested.

Form / illustrative example

An error that explains what needs to change.

BEFORE

“Invalid email” appears visually, but the field is not associated with the error and the change is not announced.

User impact A screen-reader user may not know which field needs attention or how to correct it.

THE FIX

Associate the error with the field, update the invalid state, and communicate the new message appropriately.

Form code example
<input id="demo-email" type="email"
  aria-invalid="true"
  aria-describedby="email-error">
<p id="email-error">
  Enter an email such as alex@example.com.
</p>

A connected label is also required. Validation updates the error message and invalid state; the example uses a polite status message and moves focus to an invalid field.

AFTER TRY THE CORRECTED PATTERN

Check the sample, then try alex@example.com.

Local demonstration. Nothing is sent or stored.

HOW WE VERIFY

Trigger the error using keyboard controls, read the field and its message with a screen reader, then correct the value and check again.

Error association and feedback retested.

Illustrative verification outcome. Project results are recorded after expert testing.

Modal / illustrative example

A dialog that keeps the interaction together.

BEFORE

A newsletter dialog appears while keyboard focus remains on the page behind it.

User impact Someone using a keyboard can lose context or interact with controls that should be unavailable.

THE FIX

Use an appropriately named dialog with initial focus, focus containment, closing behavior, and focus return.

Modal code example
<dialog aria-labelledby="dialog-title">
  <h2 id="dialog-title">Preferences</h2>
  <button type="button">Close</button>
</dialog>
<!-- Open with showModal(). -->

The native modal dialog makes background content inert. Opening and closing handlers set initial focus and restore focus to the opener.

AFTER TRY THE CORRECTED PATTERN

Open the dialog. Try Tab, Shift+Tab, then Escape.

Product Options / illustrative example

Product choices with names and states.

BEFORE

Color swatches are clickable divs with no reliable keyboard operation, accessible names, or selection state.

User impact A customer may not be able to understand the options or select the product they want.

THE FIX

Use named native radio buttons with a group label and a clear checked state.

Product Options code example
<fieldset>
  <legend>Headphone color</legend>
  <label><input type="radio"
    name="color" value="ivory" checked>
    Ivory</label>
</fieldset>

The full group uses a shared name and unique values. Native radios expose their names and checked states and support arrow-key selection.

SYSTEMIC REMEDIATION

One good fix can improve hundreds of pages.

Many accessibility problems repeat because they originate in a shared component, template, theme, or design pattern. We look for the source.

Illustrative finding: 83 product pages use the same inaccessible quantity selector.

Rather than handle each page as an unrelated issue, we investigate the shared product template, fix the component, and retest representative pages and relevant variations.

MORE THAN SOURCE CODE

Accessible code still has to produce an accessible experience.

Remediation isn’t complete simply because a line of HTML changed. The resulting interaction needs to be tested.

Depending on the issue and scope, verification can include manual inspection, keyboard and screen-reader testing, automated checks, responsive testing, and review of the complete user journey.

We don’t validate fixes by looking at the code alone.

THE CORRECTED EXPERIENCE, UNDER REVIEW

  1. Code inspection

    Is the markup and behavior appropriate?

  2. Keyboard

    Can someone operate it without a mouse?

  3. Screen reader

    Are names, roles, states, instructions, and changes communicated?

  4. User journey

    Can the person actually complete the task?

  5. Verified fix

    Does the corrected experience address the original barrier?
